# 208. 实现 Trie（前缀树）— 代码点评

## 使用的方法
**数组子节点 Trie**：每个 `TrieTreeNode` 持有一个定长 `next(26)` 子节点指针数组和 `isWord` 结束标记；`insert` 逐字符新建缺失分支，`search`/`startsWith` 逐字符沿 `next` 走。三个操作都只沿词长走一遍。

## 复杂度分析
- 时间复杂度: insert / search / startsWith 均 O(L)（L 为词长），与已插入词数无关
- 空间复杂度: O(节点数 × 26 × 2)（每个节点实际分配了两个 vector：`flag` 26 个 int + `next` 26 个指针）

## 代码评价
- 优点:
  - 三个方法实现正确、边界干净（断链即 return false），逻辑与标准 Trie 完全一致
  - 用 `vector(26, …)` 语义上等价定长数组，访问是 O(1)
- 可改进之处（⚠️ 与 211 超内存直接相关）:
  - **`flag` 成员完全没用**：声明并 `new` 了 26 个 int（每个节点 ≈104 字节）却从未读取，是纯浪费——本节点即 `isWord` 足够
  - **每节点两个独立 vector → 三次堆分配**：`vector<int> flag`、`vector<TrieTreeNode*> next` 各自 `malloc` 一块 + 节点本体一块，每个节点 ≈ 300+ 字节且有碎片开销。改成 `TrieTreeNode* next[26] = {}` 内嵌定长数组，只随节点一次分配，节点降到 ~216 字节且缓存友好。**211 题复用了本结构并配递归搜索，已报「超内存」**，瘦身这个节点是解 211 的首要一步（见 211 分析）
  - 可加 `startsWith` 复用 `search` 的内部遍历函数避免重复代码（本例已较短，可选）
- 代码风格: 直白、易读

## 总结
> 标准数组 Trie，三操作正确 AC，O(L) 时间达标；空间因每节点「无用 flag + 双 vector」偏肥，建议内嵌 `next[26]` 定长数组并去掉 flag——这一步同时是修 211「超内存」的关键。
> AC ✓

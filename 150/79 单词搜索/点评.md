# 79. 单词搜索 — 代码点评

## 使用的方法
**DFS 回溯 + 访问标记矩阵**：`fun(board, flag, x, y, k, w)` 先检查 `flag[x][y]` 与 `board[x][y] != w[k]` 剪枝，再标记当前格、`k++`，若 `k == w.length()` 立即成功返回；否则依次尝试上/下/左/右四个方向，返回前把 `flag[x][y]` 复位。`exist` 枚举每个格子作为起点，命中即返回。文件里另有一个早期版本 `fun1`（用 `path` 字符串和四个展开分支实现同样逻辑），但 `exist` 只调用 `fun`。

## 复杂度分析
- 时间复杂度: O(m·n·3^L·L)（L = |word|；每个起点起步 4 个方向、之后每步最多 3 个方向，每个递归帧还会按值拷贝一次整个单词）
- 空间复杂度: O(m·n)（flag 矩阵）+ O(L) 递归栈

## 代码评价
- 优点:
  - `fun` 的回溯语义完整正确：进入即判重与判字符、匹配满长度立刻返回、四个方向任一成功即真、返回前复位标记——把失败路径占用的格子释放掉，这才是能搜全的原因
  - 递归末尾 `flag[x][y] = 0;` 配合逐层返回，保证一次搜索结束后 flag 全零，不会污染下一个起点
  - `exist` 在任意起点找到串就立即返回，不再继续枚举无谓的起点
  - 主函数里用了 `ABCESEEEFS` 这种"要绕回来"的用例，比只测 `ABCCED` 更能暴露标记不复位的问题
- 可改进之处:
  - **`bool fun(..., string w)` 按值传单词**，每次递归都要拷贝一边字符串，是这份实现最大的常数开销；改成 `const string&` 立刻变快（`fun1` 同样问题）
  - **`fun1` 是死代码**：`exist` 只调用 `fun`，而 `fun1` 用 `path` 字符串比较判终止、又靠 `x++/x--` 复位，重复且容易改坏，建议整体删除，只留 `fun` 一版
  - `exist` 里 `flag = temp;` 每换一个起点就整体拷贝一次矩阵，其实 `fun` 已经保证复位，这行是冗余操作（m,n ≤ 6 时影响很小，但概念上多余）
  - 变量类型：`int b1, b2, b3, b4; b1 = b2 = b3 = b4 = false;` 用 `bool` 更自然
  - 可加两个常规剪枝：先统计 `board` 与 `word` 的字符频次，某字符不够直接返回 false；若 `word` 尾字符在棋盘上更稀有，可 `reverse(word)` 后再搜，起点数能明显减少
  - 也可以像题解解法二那样把 `board[i][j]` 临时改成 `'#'` 来省掉 `flag` 矩阵，空间降到 O(L)
- 代码风格: 注释"向下x正方向 向右y正方向"很有用；但 `fun / fun1 / b1..b4` 命名太随意，建议 `dfs` / 方向数组 `dir[4][2]` 替代四个展开分支

## 总结
> 回溯框架正确、标记复位到位、四个方向覆盖完整，AC；把按值传的 `word` 改成引用、删掉未使用的 `fun1`、去掉冗余的 flag 整表拷贝，再补上字符频次剪枝，代码会短一半且更快。
> AC ✓

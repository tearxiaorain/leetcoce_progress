# 146. LRU 缓存 — 代码点评

## 使用的方法
**手写双向链表维护访问顺序 + `unordered_map<int,int>` 存 key→value**：`head` 指向最新使用的节点，`tail` 指向最久未使用；节点用 `val` 存 key，`front`/`next` 双向串联。命中 `get`/`put` 时把对应节点提到 `head`（若命中的是 `tail` 或中部节点则相应前移）；缓存满时按 `tail->val` 逐出 key 并把 `tail` 前移一位。构造函数预分配若干空节点作"槽位"。

## 复杂度分析
- 时间复杂度: **最坏 O(capacity)**：`get`/`put` 命中中部节点时，需要从 `head` 沿链表**线性扫描**找 key 对应的节点（`map` 只存了 key→value，没存 key→节点地址）；命中头部/尾部才 O(1)。平均在访问集中于头部时较快，任意分布下退化 O(capacity)/次
- 空间复杂度: O(capacity + 操作次数)：每次命中中部/驱逐/换新都在 `head` 前 `new` 一个新节点且**从不释放**被拆下的旧节点，分配数随操作次数线性增长

## 代码评价
- 优点:
  - **语义正确**：官方示例 + 400 轮×600 次随机操作（容量 1–4，含 key=0）与标准 `list+map` LRU 的 `get` 返回值**完全一致**——命中置顶、满则逐 LRU、值更新都正确
  - 思路符合"链表序 = 访问序、头新尾旧"的经典模型，无逻辑短路
- 可改进之处:
  - **未达到题目要求的 O(1)**：应让 `unordered_map` 存 **key → 节点指针**，命中即 O(1) 定位并拆链插头，替代现在的线性扫描。顶注释已写"查找优化 map<key, node>"，正是未落地的关键一步
  - **内存泄漏**：命中/驱逐时总在头部 `new` 新节点，被移出的旧节点既不释放也不复用，分配数与操作数同阶。正确做法是逐出时**复用尾节点**（改它的 key/value 再插头），把内存压到 O(capacity)
  - 构造函数为容量预分配"槽位"节点、配合 `cnt` 计数，使空槽与真实 key 混合，代码复杂度高、易错（如 key 恰为 0 与空槽值冲突的隐患靠测试规避，未见显式防护）
  - 若平台测试规模较大，O(capacity) 扫描有超时风险——你已在平台 AC，说明用例下可过，但数据再大就不稳
- 代码风格: 单一大类 + 多处重复的"置顶"逻辑（`get`/`put` 内各复制一遍），建议抽成 `moveToHead`/`evict` 辅助函数

## 总结
> 手写双向链 LRU **语义正确**（官方示例 + 随机差分全过）且已在平台 AC；但 map 未存节点指针导致命中需线性扫描、且每操作漏一个节点——最坏非 O(1)。建议改为 `map<key,Node*>` + 复用被驱逐节点，即可稳定满足 O(1) 要求。
